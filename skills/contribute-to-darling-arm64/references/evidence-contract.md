# Evidence contract — darling-arm64

What a contribution must carry before it can be accepted. This is stricter than most
repositories, for a reason: three claims in this project's own record were withdrawn by
its own controls, and two of the first six "findings" were artifacts of the environment
rather than defects in the code.

## 1. Name the architecture

State `uname -m` for every host that produced a number, and which host produced which.

- The Darling runtime host must be **aarch64 Linux**.
- Native ground truth must come from **arm64 macOS**.
- An x86_64 result is not weaker evidence here. It is *no* evidence: Darling is a
  translation layer, not a CPU emulator, so the host architecture must match the binary
  architecture.

## 2. Name the control

A rate is a claim about an environment until a control says otherwise.

State what your control was, and how many variables you moved relative to it. If you
changed the branch, the distro, the compiler and a patch at once, you have measured
nothing attributable. Move one.

## 3. A/B/A for anything called a fix

The effect must track the patch **and** reverse on revert:

- **A** — baseline, n runs, rate recorded.
- **B** — patch applied, same n, same environment, rate recorded.
- **A′** — patch reverted, same n, rate returns to baseline.

Without A′ you have a coincidence. Report n, the effect size, and the uncertainty.

## 4. Report uncertainty honestly, and label trends as trends

The standard already set in the record: `darlingserver#17`'s *mechanism* is proven — core
dump, `TRAP_BRKPT`, exact PC, `x0=MACH_RCV_TIMED_OUT` — while its end-to-end effect is
reported as a **trend, not a proven effect** (18%→8%, p=0.23 at n=50).

An honest trend labelled as a trend is accepted. A confident claim resting on a weak n is
rejected. Overstating is the one error that costs more than being wrong.

## 5. Report failure verbatim

Paste the **first** error, not the tail. CMake and make both bury the root cause above
hundreds of follow-on lines; a pasted tail is not a diagnosis.

A clean, reproducible negative result is an accepted outcome. "It did not work" without
the output is not.

## 6. Ship the harness

Add the harness that produced your evidence to `tools/`, named after the finding it
produced (`fNNN-*`). Add the finding to `FINDINGS.md` with its citation, and the
reproduction path to `REPRODUCE.md` if it establishes a headline claim.

A number in `FINDINGS.md` must lead someone else to the tool that measured it. If your
evidence cannot be regenerated by a stranger, it is not evidence yet.

## 7. Correct the record in place

If your result overturns something already recorded, cite the finding you are overturning
and leave the retraction in place next to the evidence that falsified it. Do not silently
reword or delete a superseded claim — the retractions are part of what makes the rest of
the record trustworthy.

## 8. Redistribute nothing Apple owns

The dyld shared cache, application bundles, the Swift toolchain and all corpus binaries
stay on the machine that captured them. Never commit them, and never add a test that
requires them to be published.

## 9. Preserve upstream attribution

Never vendor or copy code or text from forks that strip upstream GPL-3.0 attribution. One
such fork was evaluated and rejected on exactly that ground; reintroducing its code would
propagate a licence defect into this repository and into anything downstream of it.
