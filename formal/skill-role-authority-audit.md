# Skill source authority by role

The existing `skill_source_authority` model required a D1 manifest and an open
project on every path. Source review found that this described only generated
contributor admission. The runtime has three distinct paths in
`expected_skill_bytes`:

- A static canonical skill requires exact template bytes and rejects any
  registry binding. It does not read a generated-project manifest.
- A generated reviewer skill requires the pinned D1 revision/digest and exact
  generated bytes. It does not require the project to be open to contributors.
- A generated contributor skill requires both the pinned manifest and a
  successful current-project admission observation.

The model now represents all three roles and binding presence. The four
original contributor scenarios remain; seven new scenarios cover static and
reviewer success/refusal and missing generated bindings. The transport retry
bound remains three attempts for the represented request. This does not model
every network call as one shared retry counter.

No runtime policy changed. In particular, this does not restore template
freshness, ancestry, release-label or revocation gates. Project openness is the
runtime's observed admission fact, not a guarantee that a later unrelated
request cannot change project state. Full schema validation, file-tree and
cryptographic byte verification remain external predicates in this model.

All 11 scenarios are unexecuted. No installer, parser, test, simulator,
verifier or application ran for this source-model correction.
